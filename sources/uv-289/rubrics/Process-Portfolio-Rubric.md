# Process Portfolio & Presentation Rubric (75 pts)

**Assignment**: M08-A2 — Process Portfolio & Presentation
**Module**: 8 — Final Delivery (Weeks 15-16)
**CLOs Assessed**: 1 (Autonomous PM), 2 (Cross-Team Collaboration), 4 (Adaptive Planning), 5 (Documentation)
**Point Distribution**: Portfolio Completeness (20) + PM Reflection Essay (20) + Presentation Quality (20) + PM Mastery Evidence (15) = **75 pts**
**Context**: This rubric evaluates the process portfolio and final presentation component of M08-A2. The technical deliverable (M08-A1, 100 pts) is graded separately. Together they constitute Module 8's 175-point Apply phase.

---

## Criterion 1: Portfolio Completeness (20 pts)

### Sprint Documentation Archive (8 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | All 8 sprint planning documents are present and organized in a logical directory structure (e.g., `/docs/process/sprint-1/` through `sprint-8/`). Each sprint folder contains: planning doc, standup log, review notes, and retrospective. Documents are internally consistent (Sprint 3 retro references Sprint 2 action items). File naming follows a consistent convention. Documents are written artifacts with sprint-specific content, not empty templates. Visible evolution in planning sophistication from Sprint 1 to Sprint 8. | 8 |
| **Proficient** | 6-7 sprint documentation sets are complete. 1-2 sprints have partial documentation (e.g., missing retrospective or standup log is incomplete). Organization is reasonable but may not follow a strict directory convention. Documents contain actual sprint-specific content. | 6-7 |
| **Developing** | 4-5 sprint documentation sets are present. Several sprints have significant gaps (missing planning docs or retrospectives entirely). Organization is inconsistent: some documents properly placed, others scattered or in the repository root. Some documents appear to be last-minute reconstructions rather than contemporaneous artifacts. | 4-5 |
| **Beginning** | Fewer than 4 sprint documentation sets, or documentation is clearly fabricated after the fact (all documents have the same creation date in Week 16, content is generic and interchangeable between sprints). Portfolio is a shell of templates with placeholder text. | 0-3 |

### Supporting Artifacts (7 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Portfolio includes all of the following with substantive content: risk register (updated throughout the semester with timestamped entries, not just the Week 1 original), burndown or velocity chart showing trajectory across all 8 sprints with planned vs. actual data, CLAUDE.md file (for Sprints 5-8) with meaningful AI context documentation, and a professional README that a stranger could use to clone, install, configure, and run the project. Artifacts cross-reference each other (e.g., velocity chart data matches sprint planning docs, risk register entries appear in retrospectives). | 7 |
| **Proficient** | Most supporting artifacts are present (risk register, velocity data, CLAUDE.md, README). 1-2 artifacts are thin or incomplete (e.g., risk register was not updated after Sprint 3, or CLAUDE.md is a single paragraph). README exists and is functional but may lack some setup detail. | 5-6 |
| **Developing** | Some supporting artifacts present but several are missing entirely. Risk register is a Week 1 artifact never updated. No velocity chart or burndown visualization. CLAUDE.md is missing or is a single line. README exists but does not enable project setup. | 3-4 |
| **Beginning** | Supporting artifacts are largely absent. No risk register, no velocity tracking, no CLAUDE.md, or README is the default GitHub template with no project-specific content. Portfolio contains sprint documents only, with no evidence of the broader PM toolkit. | 0-2 |

### Portfolio Organization & Narrative (5 pts)

| Level | Description | Points |

## Criterion 2: PM Reflection Essay (20 pts)

### CSC-113 to CSC-289 Journey Narrative (5 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Essay traces the student's PM skill development across the full course sequence (CSC-113, CSC-114/CTS-285, CSC-289) with specific examples from each stage. Student articulates what they could do at each stage that they could not do before (e.g., "In CSC-113 I followed a template for user stories; by CSC-289 I was writing Given-When-Then acceptance criteria and evaluating design assets against them autonomously"). Growth is concrete and evidence-based, not just "I got better." The narrative is personal and authentic, not a course catalog description. | 5 |
| **Proficient** | Essay references the course sequence and describes growth, but examples are somewhat generic or concentrated in CSC-289 without deeply reflecting on earlier courses. Student acknowledges the progression but does not articulate specific skill transitions at each stage. | 4 |
| **Developing** | Essay mentions prior courses in passing but the reflection is surface-level (e.g., "I learned a lot in CSC-113"). No specific examples of skill development across the sequence. CSC-289 experience dominates with little connection to foundational courses. | 2-3 |
| **Beginning** | No reference to prior courses. Essay treats CSC-289 as an isolated experience. Student cannot articulate how earlier coursework prepared them for capstone-level autonomy. | 0-1 |

### What Worked / What Didn't Analysis (5 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Essay identifies 3+ specific PM practices that were valuable with concrete evidence of impact (e.g., "Daily standups prevented the 'lost week' problem I had in CTS-285 Sprint 2 -- in CSC-289 I caught the OAuth blocker on Day 3 instead of discovering it at sprint review"). Also identifies 2+ practices that did not work or that the student would change, with honest root-cause analysis (not blame-shifting). Analysis demonstrates genuine self-awareness and process maturity. | 5 |
| **Proficient** | Essay identifies practices that worked and practices that did not, with some specific evidence. Analysis is honest but could go deeper: student identifies surface symptoms rather than root causes (e.g., "standups helped" without explaining the mechanism, or "I procrastinated" without analyzing what enabled procrastination). | 4 |
| **Developing** | Essay lists practices that worked and did not work, but without specific evidence or analysis. Reads like a bulleted list rather than reflective writing. "What didn't work" section is defensive or blames external factors (instructor, designer, technology) rather than examining the student's own process decisions. | 2-3 |
| **Beginning** | Essay does not distinguish between effective and ineffective practices, or claims everything worked perfectly (no self-awareness). Alternatively, essay is entirely negative with no acknowledgment of what went well. | 0-1 |

### Adaptive Moments (5 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Essay describes 2+ specific moments when the project plan changed, with detailed analysis of: the situation that triggered the change, the options considered, the decision made and why, and the outcome. Student evaluates whether the adaptation was the right call in hindsight. At least one example involves a scope management decision (cut, defer, or pivot). Adaptive moments are connected to risk register entries, retrospective action items, or velocity data. | 5 |
| **Proficient** | Essay describes 1-2 adaptive moments with context and decision rationale. Analysis is present but may lack the "in hindsight" evaluation or connection to formal PM artifacts. Student demonstrates adaptive thinking but the reflection is not as rigorous. | 4 |
| **Developing** | Essay mentions that plans changed but does not analyze the decision-making process. Adaptation is described as something that happened to the student rather than a deliberate PM decision. No connection to scope management, risk mitigation, or retrospective learnings. | 2-3 |
| **Beginning** | No adaptive moments described, or student claims the original plan worked perfectly from Week 1 through Week 16 (which is not credible for a 16-week capstone). No evidence of reflective thinking about change management. | 0-1 |

### Career Application (5 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Essay explicitly connects PM skills developed in CSC-289 to professional career contexts. Student identifies specific skills they will use in a junior developer role (e.g., "sprint planning translates directly to Jira workflow at most Agile shops," "the GRD collaboration taught me how to give feedback to designers using SBI, which I will use in cross-functional product teams"). Essay addresses both technical PM skills (estimation, velocity, risk management) and interpersonal PM skills (communication, collaboration, feedback). Student identifies 1-2 PM skills they still want to develop with a concrete plan. | 5 |
| **Proficient** | Essay connects CSC-289 skills to career readiness at a general level (e.g., "Agile is used in industry so this experience is valuable"). Some specific connections are made but the analysis stays at a surface level. Student acknowledges areas for growth but without specificity. | 4 |
| **Developing** | Career connection is an afterthought (single paragraph, generic statements like "this will help me get a job"). No specific mapping of demonstrated skills to professional contexts. No self-identified growth areas. | 2-3 |
| **Beginning** | No career application section, or career connection is a single sentence. Student does not demonstrate awareness of how capstone PM skills transfer to professional software development work. | 0-1 |

## Criterion 4: PM Mastery Evidence (15 pts)

### Retrospective Action Items Implemented (4 pts)

| Level | Description | Points |
|-------|-------------|--------|
| **Exemplary** | Portfolio demonstrates a clear feedback loop across sprints: retrospective action items from Sprint N appear as implemented changes in Sprint N+1, with the next retrospective evaluating impact. Student can point to 3+ specific examples of action items that measurably changed their process (e.g., "Sprint 3 retro action: 'Start PRs by Wednesday.' Sprint 4 evidence: 4/5 PRs opened by Wednesday. Sprint 4 retro: 'Wednesday PR start gave me 3 days of review time instead of 1 -- keeping this practice.'"). Cumulative evidence shows iterative improvement, not just individual corrections. | 4 |
| **Proficient** | 2+ action items are traceable from retrospective to implementation. Evidence exists but the student does not always close the loop (action item implemented but next retro does not evaluate its impact). Pattern of improvement is visible but not rigorously documented across all sprints. | 3 |
| **Developing** | 1 action item is traceable from retro to implementation. Most retrospective action items are not referenced in subsequent sprints. Improvement may have occurred but the portfolio does not document the connection between retro actions and process changes. | 1-2 |
| **Beginning** | No traceable connection between retrospective action items and subsequent process changes. Retrospectives exist in isolation with no evidence of follow-through. Student cannot identify a single retro action that changed their behavior. | 0 |

## Canvas Setup Recommendations

1. **Create as a single Canvas assignment** (M08-A2: Process Portfolio & Presentation, 75 pts) with this rubric attached.
2. **Submission format**: Accept GitHub repository link (for portfolio documents) + slide deck upload (PDF) + reflection essay (Markdown, PDF, or Google Doc link) + recording link (for online students).
3. **Grade in two passes**: First pass scores portfolio completeness and essay criteria from the submitted repository and essay document. Second pass scores presentation quality and PM mastery evidence criteria during or immediately after the live presentation.
4. **Presentation scheduling**: Schedule 15-minute blocks per student (10-12 min presentation + 3-5 min Q&A). Allow 5 minutes between students for grading notes. A class of 15 students requires approximately 5 hours of presentation time across 2-3 class sessions in Week 16.

6. **Feedback timeline**: Per the canonical coursemap RSI requirements, provide comprehensive written feedback within 5 business days of the Week 16 deadline. Feedback should be CLO-by-CLO where possible.

## Instructor Notes

### Distinguishing Portfolio Quality from Sprint Quality

This rubric evaluates the portfolio as a compiled and reflective artifact, not the quality of individual sprints (which were already graded using the Sprint Process Rubric throughout the semester). A student who struggled in early sprints but compiled an honest, reflective portfolio demonstrating growth and self-awareness can score well here. Conversely, a student with excellent sprint scores who submits a disorganized, unreflective portfolio may score poorly. The portfolio is about synthesis, reflection, and narrative -- not just completeness.

### Handling the PM Reflection Essay

The reflection essay is the most subjective component. Key quality indicators:
- **Specificity**: Does the student cite specific sprint numbers, story point values, dates, and decisions? Or do they speak in generalities?
- **Honesty**: Does the student acknowledge genuine failures and mistakes? Or is the essay performatively positive?
- **Growth evidence**: Can the reader trace a developmental arc from the essay? Or does the student describe CSC-289 as a static experience?
- **Career connection**: Does the student make concrete, plausible connections to professional work? Or is the career section a formulaic afterthought?

### PM Mastery Evidence Assessment

The PM Mastery Evidence criterion (15 pts) requires the instructor to cross-reference portfolio claims against actual repository artifacts. Specifically:
- **Retro action items**: Check that cited action items actually appear in the retrospective documents and that the claimed implementations are visible in subsequent sprint artifacts.
- **Velocity data**: Verify that velocity numbers match sprint planning documents and GitHub activity (commit frequency, PR merge dates).
- **Scope decisions**: Confirm that cited scope changes are reflected in GitHub Issues (label changes, closure rationale, "Won't Have" items).
- **Communication evidence**: Verify that communication logs contain actual message content, not just summaries.

### Presentation Assessment Protocol

Grade the presentation in real-time using a printed or digital copy of Criterion 3. Take brief notes during Q&A for the "Q&A Readiness" sub-criterion. If recording presentations, note timestamps for key rubric moments to reference in written feedback. Consider having students present in alphabetical order with a visible timer.
