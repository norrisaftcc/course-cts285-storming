🛑 FEATURE FREEZE — After Week 13, No New Features

This is not a suggestion. After Week 13, your project enters feature freeze. From that point forward, only bug fixes, polish, and documentation are permitted. No new features, no "one more thing."

Why? New features introduced at the end of a project are the #1 cause of broken deployments, missed deadlines, and last-minute disasters. Professional teams enforce feature freeze for exactly this reason.

What this means for you:

  • Any feature not complete by end of Week 13 gets cut — no exceptions
  • Week 14 is exclusively for bug fixes, deployment, testing, and documentation
  • Your Feature Freeze Commitment (25 pts) formally documents what is in and what is out

🎭 Role Focus: QA Lead + Developer

Your mindset shifts this sprint.

You are no longer building new features — you are hardening what you have. As QA Lead, you think about what can go wrong. As Developer, you fix it. This is the sprint where your application becomes reliable, deployed, and professionally presentable.

Key Responsibilities:

  • Identify and handle edge cases — what happens with empty inputs? Invalid data? Network errors?
  • Implement error handling, input validation, and graceful degradation
  • Deploy your application to a live URL (not localhost)
  • Document every deployment step so someone else could replicate it
  • Conduct comprehensive testing: functional, edge case, and accessibility
  • Build a testing evidence portfolio with screenshots and results
  • Commit to feature freeze — document what is in scope and what is cut

Professional Reality: QA is not something you do at the end. It's a mindset. The best developers think about failure modes while they're writing code, not after.

🔬 Hands-On Activity: Deployment Dry Run Lab

What you'll experience:

You will deploy your capstone application to a staging environment for the first time. This is intentionally done early in the module so you have time to fix deployment issues before the final submission.

What You'll Practice:

  • Configuring environment variables for a production environment
  • Setting up a database on a remote server
  • Running build and deployment commands
  • Debugging deployment-specific issues (works on localhost but not in production)
  • Writing deployment documentation that another developer could follow

Common Gotchas:

  • Hard-coded localhost URLs that break in production
  • Missing environment variables
  • Database connection strings that only work locally
  • Static files not served correctly in production
  • CORS issues when frontend and backend are on different domains

Your application MUST be accessible at a live URL — not localhost — for your final submission.

💡 Andrew's Tips for Success

  • Deploy early, deploy often: Do the Deployment Dry Run in Week 12, not Week 14. Every deployment reveals issues you didn't expect. Give yourself time to fix them.
  • "It works on my machine" is not deployment: Your capstone must be accessible at a live URL. Period. Start figuring out deployment now.
  • Edge cases are where your app shows its character: What happens when a user submits an empty form? Types SQL into an input field? Refreshes mid-transaction? Handle it gracefully.
  • Feature freeze is liberating, not limiting: Once you commit to what's in scope, all your energy goes to quality instead of chasing "one more feature."
  • Accessibility is not optional: Run a Lighthouse audit. Fix the critical issues. Your users deserve an accessible application.
  • Document while you deploy: Write down every step AS you do it. If you try to reconstruct deployment docs from memory, you will miss steps.

📣 Andrew's Note

This is the module where your capstone stops being a class project and starts being a real application. When you deploy to a live URL, anyone in the world can see your work. That changes how you think about quality.

I know feature freeze feels painful. You have features you wanted to build. Ideas you're excited about. But shipping a polished application with fewer features beats shipping a broken application with more features — every single time. Employers want to see that you can deliver, not that you can start.

You've been on this journey since CSC-113 when you were learning what a user story is. Now you're deploying production applications and conducting accessibility audits. Take a moment to appreciate how far you've come.

Feature freeze is a professional discipline. Embrace it. Your future self — and your users — will thank you.
